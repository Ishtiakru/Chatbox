# Saira / Chatbox

A mobile-friendly prototype for a messaging app with an assistant and an admin area. Google sign-in is configured through Firebase. Experimental Firestore chat, AI and admin code exists behind off-by-default build flags, but has not been deployed or verified end to end. Android and installable web app foundations are present but have not been released; a diagnostic Android debug build succeeded in the user's Cloud Shell and the user reported downloading it. This is not a production chat service.

## Run locally

Requires Node.js 22.12+ (Capacitor 8 and the Functions backend require Node.js 22).

```sh
npm install
npm run dev
```

Open the address printed by Vite. `npm test` runs the small offline-guide test suite; `npm run build` produces a static build.

## What works today

- Sign in and out with Google through Firebase Authentication once the project is configured as described below. Sign-in does not grant admin access.
- Browse and search sample conversations; send local-only messages that persist in this browser's local storage. Sample people and messages are illustrative and are not real accounts.
- Ask Saira's deterministic offline guide questions about the prototype. This is **not** an AI model and does not automatically learn about future changes.
- View the locked admin and call placeholders. Experimental Live chats, Saira AI and admin features are disabled until explicitly enabled and configured. The default build does not send messages to other users, make calls, grant admin access, or modify application code.
- The new source includes installable web-app metadata and a minimal offline notice. This has been smoke-tested locally, but is not yet deployed to Hosting. It is not an APK and the offline notice does not provide offline chat.

Do not put private information in the demo: local storage is not encrypted and can be accessed by scripts on the same origin or by anyone using the browser profile.

## Firebase sign-in setup

This app uses the Firebase web configuration for project `chatbox-afb8c`. Firebase web configuration (including its API key) identifies the project and is public client configuration, **not** a secret or a grant of access. Do not put service-account keys, AI provider keys, or other private credentials in the browser or repository. Enforce access using Firebase Security Rules and trusted backend authorization.

1. In Firebase Console, enable **Authentication → Sign-in method → Google** and provide any requested support email.
2. In **Authentication → Settings → Authorized domains**, add the exact hostname used by the deployed app or preview (without a scheme, port, or path). Add new preview hostnames when they change. Do not authorize untrusted domains. Enable pop-ups in the browser if needed.
3. Test sign-in and sign-out on the actual authorized domain. Preview iframes or browser privacy settings may block pop-ups; use an authorized top-level site if necessary. Google sign-in has not been verified until those console steps and an interactive login succeed.

Sample conversations and local messages remain shared within the same browser profile after signing in or out; they are not synced with Firebase and are not private account data. Don't use the demo for sensitive conversations.

## Experimental Firestore direct chat (isolated test only)

The source includes an opt-in two-person chat prototype. Users who sign in publish only a UID and display name in `profiles/{uid}`. Each user can share their UID privately; another signed-in user who knows the exact ID can request a conversation. The recipient must accept before either participant can send messages or initiate calls. Either participant can close the conversation, after which the messages remain readable but no new messages can be sent. The selected conversation observes its peer’s profile by exact UID and displays the user-provided name with an explicit unverified label, while keeping the UID visible; cache-only and pending snapshots are not used as confirmed names. A profile-listener failure only hides the name. This costs an additional document listener/read and changes may consume Firestore free quota. **Any signed-in user who knows a UID can directly read that profile under the candidate rules**, whether or not they are a conversation member; blocking does not hide it. The name is not verified identity and must not be used for authorization. Its members can see the latest 100 messages in real time, with older messages fetched in pages from the server. Earlier messages are retained when successive server windows overlap. Cached fragments are marked potentially incomplete and cannot anchor pagination. If the server window moves completely beyond the previous one, the client refreshes the visible window and allows earlier messages to be reloaded from its new boundary instead of silently skipping the intervening history. In-flight older pages from the previous boundary are discarded. This assumes immutable, timestamp-ordered messages as enforced by the candidate rules; cached metadata is not a reliable connection monitor. The in-memory feed is cleared when changing threads or signing out. Unsent live-message drafts and send errors are kept separately per conversation in memory while switching threads; they are not stored on disk and are cleared on refresh, sign-out, account changes or a terminal listener error. Acknowledged sends clear only the matching draft, including when the user has switched threads; rejected drafts remain available while that live session remains open. Signing out, a session reset or refreshing does not necessarily cancel a pending write; it may still commit later, so an uncertain result is not safe to blindly retry. While a live request, message, block change or initial profile connection remains visibly pending, sign-out asks for confirmation about that unknown outcome; this warning does not track writes after a session reset or prove cancellation. New conversation requests require a server-confirmed peer-profile lookup, so they cannot be created offline. The client checks the initiating Firebase account and live-session generation before profile registration, after the lookup and before starting its request write, but cannot cancel a Firestore operation already in flight. Firebase rules remain the authorization boundary. A terminal conversation or message listener error clears the active live session and stops local call media; the user can explicitly reconnect. Failed older-page reads remain retryable without resetting the session. This behavior is not a substitute for server authorization. Optimistic writes are marked as sending until acknowledged; a rejected or displaced unacknowledged message is removed rather than retained as sent. A server acknowledgement does not prove that the recipient received or read the message. In the experimental UI, a request, response, or message that is still awaiting the service after eight seconds shows an unknown-outcome notice; this timer does not cancel, retry, or mark the operation as failed. Firestore writes can remain pending while offline. Check the conversation after reconnecting before retrying, since a pending write could later succeed. This notice is informational, not a connection monitor or delivery receipt. Pagination was tested with simulated identities in Firenook and the official local emulator, not real accounts or phones. Rejected-write and completely displaced-window feed behavior have been tested with simulated accounts in Firenook and the official emulator, not with real accounts. Fetching older pages requires a working network. Messages are stored in Firestore; unlike the demo, they are not local-only. The client does not list profiles or collect email addresses in Firestore.

**Default-off blocking lab (not production protection):** a private `userBlocks/{owner}/blocked/{peer}` record allows only its owner to list/create/delete it. Candidate rules consult both directions before new conversation requests, pending-request acceptance, message writes, and new call/ICE signaling. Participants retain access to existing history; either can still close the chat or end a call. Unblocking does not require fresh consent for an already-active conversation: it may allow interaction to resume. Blocking does not close existing peer-to-peer media, delete history, stop profile lookup, stop multiple-account abuse, notify the other side, or prevent all races while an operation is in flight. A user-facing experimental control is available only with both `VITE_ENABLE_FIRESTORE_CHAT=true` and `VITE_ENABLE_EXPERIMENTAL_BLOCKING=true`. It closes local calls before starting a block, disables messaging/calls while block state is not server-confirmed, and waits for write acknowledgement plus a matching server snapshot before displaying a confirmed block or unblock. The experimental client service can atomically add a block and close one selected conversation; if the selected chat was concurrently closed or access denied, the whole batch fails and no block is confirmed. Other active conversations are not closed, and unblocking can restore interaction in them. A write is not confirmed until its promise resolves; cached or pending snapshots must not be presented as successful protection. The changed rules, controller and service are undeployed. Simulated-account tests passed on Firenook and, for the combined candidate, the official emulator; control rendering was smoke-tested in a mobile-sized browser, not with real accounts. Privacy UX, two-device/network testing, rate limits and independent security review remain mandatory. Do not present this as active user protection.

**This is not production-ready or end-to-end encrypted.** Display names can be looked up by any authenticated user who knows a UID. There is no production-ready blocking, spam protection, rate limiting, message deletion, push notification, moderation, account deletion, or reliable deduplication of conversations. Anyone with a known UID can send repeated requests; closing a conversation does not block the sender from creating another. The blocking lab is default-off and is not deployed; simulated coverage for the combined candidate passed the official emulator. Active peer-to-peer media may continue if a device misses a closure update while offline. The previous combined candidate including the consent rules passed 23 simulated tests on the official local emulator in Cloud Shell. The updated call policy passed simulated official-emulator tests in the combined candidate; calls have not been tested against a real Firebase project. A two-UID-restricted base chat variant was reportedly published to a separate test project, with limited real-browser evidence described above; this is not a production deployment or security review. Existing prototype conversations without the new status fields require an explicit reviewed migration; they cannot be used as active conversations. Do not use sensitive information, deploy as-is, or treat the sample rules as a complete production security review.

Both use `demo-chatbox` and do not deploy to Firebase. On 2026-11-21 the isolated v4 package ran the combined candidate with `demo-chatbox` on the official Firestore emulator in Cloud Shell: 23 tests passed and none failed. This was a simulated test, not a deployment. The current standalone base, admin and call candidates also passed simulated official-emulator tests in [GitHub Actions run 44923220625](https://github.com/Ishtiakru/Chatbox/actions/runs/44923220625). Re-run official tests when code or rules change.
2. Set up a **separate test Firebase project** with Google Authentication and Firestore. Review `firestore.rules` with a security reviewer; deploying rules replaces existing rules. Use only test accounts and data. Deploy the reviewed rules to that test project before testing writes. 3. Only in a controlled test build, set `VITE_ENABLE_FIRESTORE_CHAT=true` before starting Vite or running `npm run build`. The default is false. Verify sign-in, permissions, cross-account access, failures and sign-out using two accounts, including that a third account cannot read or write either user's messages. ## Experimental call signaling rules (not deployed)

`firestore.calls.rules` is a separate **base-chat-only** candidate, not combined with the Spark admin candidate and not selected by `firebase.json`. It sketches participant-only calls, receiver-only acceptance, per-side ICE candidate writes and a five-minute signaling expiry. The earlier version of the call policy was included in the combined candidate that passed 23 simulated official-emulator tests. The updated expiry/end policy passed simulated official-emulator tests both standalone and in the combined candidate in GitHub Actions run 44923220625. It has not been tested with real Firebase users or phones. Do not deploy without independent security review and real-device validation.

`src/call-session.js`, `src/firestore-call-transport.js`, and `src/call-controller.js` implement experimental orchestration and signaling. A browser-only lab panel is wired behind both `VITE_ENABLE_FIRESTORE_CHAT=true` and `VITE_ENABLE_EXPERIMENTAL_CALLS=true`; both default to off. When local tracks exist, its microphone and camera controls toggle the actual tracks in the current peer stream. Disabling a track suppresses outgoing content, but does not revoke permission or guarantee that device capture or the hardware indicator stops; end the call to stop tracks. The controls have local unit tests and a same-browser fake-media test, not real-phone or independent privacy verification. It is not deployed and is not enabled on Android. Only the selected conversation is watched. When the page reports it is hidden or leaves Live chats, the app invalidates in-flight call initialization and disposes local media and discovery; returning recreates discovery but does not automatically resume a call. Start, review and accept controls require the visible, active Live page and current account. The media permission wrapper checks availability before and after the prompt and stops tracks from a late grant if the page or initiating session is no longer available. A mocked full-page browser test with fake microphone/camera tracks exercised delayed grants, hiding and navigation; it is not a real-device test. These are best-effort client checks, not a guarantee that every platform immediately reports suspension. A recipient must explicitly accept before media is requested. A client-side setup deadline ends calls that do not connect within 60 seconds (including unanswered calls or a stalled permission prompt), and a reported WebRTC disconnection gets a 20-second reconnection grace period before local teardown. A late permission grant after timeout is stopped. These are best-effort client timers: browser suspension or absent/delayed connection-state events can delay or prevent them, and the other peer may not receive an end notification. Cached-only incoming calls are hidden and, after a server-confirmed call snapshot, a cache fallback stops local media and listeners. Firestore metadata is not a reliable or immediate connectivity signal; a missed closure or undetected connectivity loss can still leave media running, and an offline peer may not receive the end notification. The lab panel and controller have also been exercised together in an isolated same-browser harness with fake media, simulated authenticated accounts, and Firenook signaling; this is not an end-to-end test of the full app or real devices. The Firestore transport has been tested with synthetic identities on Firenook and a same-browser WebRTC loopback using fake camera and microphone tracks. The current combined candidate passed simulated Firestore transport and policy tests on the official emulator; actual accounts, separate phones and real networks are still needed. Authentication and authorization depend on Firebase and the candidate rules, not client-supplied UID values. Calls remain unavailable in the default app and the deployed site; the optional lab requires candidate rules in an isolated test environment. Firestore rules alone do not prevent spam, cap candidate documents, clean up data, or prevent signaling metadata/IP addresses from being exposed to the other participant. This candidate has no retention/cleanup or abuse controls. New acceptance and ICE signaling expire after five minutes even for accepted calls, which can prevent later reconnection. The updated candidate allows either participant to end the record after expiry; this behavior has simulated coverage on Firenook and the official emulator, not real accounts. A security-reviewed transport, complete consent UX, lifecycle/cleanup, expiry handling, quotas, STUN/TURN design and real two-device tests are still necessary. TURN may incur costs and direct calls will fail on some networks without a relay.

## Experimental per-account message cooldown (not deployed)

A separate review-only candidate, `firestore.rate-limited-experimental.rules`, layers a two-second per-account message cooldown onto the existing combined candidate. Generate it with `npm run generate:rate-rules`. It is **not** selected by `firebase.json`, and nothing here deploys it. With both `VITE_ENABLE_FIRESTORE_CHAT=true` and `VITE_ENABLE_EXPERIMENTAL_MESSAGE_COOLDOWN=true`, the client sends a message and a private, per-account reservation in one atomic batch; this client setting must only be paired with the matching candidate in an isolated test environment. Enabling only one side makes sending fail. Rules bind the reservation to exactly one new message and use server request time, across all conversations and devices for an account. Simulated tests cover bypass attempts, blocks, consent, parallel sends, and the client batch. `npm run test:rate:alternate` uses Firenook; `npm run test:rate` uses the official local emulator. The candidate-specific official-emulator suite also passed in GitHub Actions run 44920593939. Real account/device tests and independent security review are still required.

This is a narrow speed bump, **not** complete spam or quota protection: it does not limit new accounts, invitations, calls, failed requests or overall activity, and several accounts can bypass a per-account cooldown. Each accepted message now also writes a throttle document and rule checks may consume extra reads, reducing the available free quota. Rapid legitimate messages across chats or devices may fail; the draft remains for retry after a rejected write. If offline, a write may remain pending with an unknown outcome; never assume it was rejected or retry blindly while it is pending. Migration, abuse detection, privacy, retention and resilience need further design before production use.

The Functions AI prototype sends only the question the user submits and the curated knowledge to OpenAI; other chat history is not sent. Questions may contain personal data, so users must be informed and should not submit sensitive information. The model can be inaccurate. `docs/saira-knowledge.md` is the curated source; `npm run build` regenerates `functions/knowledge.generated.json` including a version and content hash. The default Firebase configuration does not include Functions or an automatic Functions predeploy hook. Developers must review and update the knowledge text for every release and redeploy the backend: generating a file does not automatically discover or publish all changes.

The admin prototype checks a server-controlled `system/admin` UID, not an email entered in the client. Every privileged write rechecks that UID inside a transaction, writes an audit record and only permits a confirmed public welcome-message update. AI-generated proposals are strictly allowlisted; it cannot edit source code, deploy changes or execute arbitrary commands. Admin transfer requires a recent sign-in, explicit confirmation, and an active target with a verified email. There is no multi-admin support or complete account-recovery flow. `functions/bootstrap-admin.js` is a one-time trusted-server script; it requires project-owner authorization and will not replace an existing admin. Do not run it or deploy this prototype without a security review, backup/recovery plan, separate test project, and tests of authorization, App Check, rate limits, abuse, billing and races. Unit tests use mocks, not deployed services.

## Next: production services

Complete and validate the Firestore prototype, add proper user profiles and message storage, and add abuse prevention. Google sign-in alone is not administrator authorization. Bootstrap the first administrator through a trusted server-side process, verify Firebase ID tokens on the server, and enforce admin roles using server-managed custom claims or a server-controlled role record. Admin transfer must be audited and performed by a protected backend, with explicit confirmation and a policy preventing accidental loss of all admins. Never accept an admin email or role from client input as proof of authority.

Real voice/video calls need signaling, WebRTC, STUN/TURN, permissions and abuse controls. A real Saira needs a server-side AI provider and a versioned, curated knowledge source that is updated as part of releases; do not expose API keys in the client. Natural-language admin requests should be interpreted by a trusted backend into a small allowlist of validated operations, with preview, authorization, audit logs and confirmation—not arbitrary code execution. Building or deploying code changes requires a separate reviewed deployment pipeline.

## Firebase Hosting deployment

`firebase.json` configures Hosting only; it does not select any Firestore rules or Cloud Functions. This avoids including the experimental chat rules or potentially billed Functions in a default deployment. It does not protect against publishing an unsafe Hosting build, an explicitly selected alternate config, or changes made through the console. The local-only test scripts pass `--config firebase.emulator.json --project demo-chatbox`; that separate config references the base **experimental** rules. Never use it for deployment or point it at a real project. These local configuration changes do not alter the live Firebase project.

Hosting serves the pre-built `dist` directory from the `chatbox-afb8c` project. To deploy the prototype, sign into the Firebase CLI on a device or Cloud Shell with permission to deploy to that project, then run:

```sh
npm ci
npm test
npm run build
npx firebase-tools deploy --only hosting --project chatbox-afb8c
```

Deployment publishes the prototype to the project's Hosting site and may replace an existing deployment. Verify the target project and site first. The built-in `chatbox-afb8c.web.app` domain should already be an authorized Firebase Auth domain; confirm in Authentication settings before testing Google sign-in. The default build does not enable live chat, calls, admin access, or AI. Firestore rules require a separate reviewed deployment; `--only hosting` does not deploy them. Never share Firebase login credentials or service-account keys.
