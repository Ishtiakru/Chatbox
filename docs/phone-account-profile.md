# Phone-number account and profile: unfinished design and isolated prototype

Owner request: phone number + password login; no SMS, verify the personal Gmail using an email link; each user has a photo and a unique six-digit contact ID and can request a connection by number, ID or QR. Existing Google/test-account access must not be silently disabled.

## Prototype in this repository

`src/profile-identity.js` and `scripts/generate-profile-identity-rules.mjs` are **local-emulator-only preparations** for atomic six-digit code reservation and a versioned QR text payload. The rules are derived from a pinned combined template and are not selected for deployment. They do not preserve the isolated live project's additional two-UID restriction on their own. The login screen now shows disabled phone/password and account-creation controls with an explicit unavailable notice; existing Google sign-in remains connected. No phone login, camera scanner, profile/photo upload, phone lookup, email sign-up or production identity use is connected by these files. Six digits provide only one million possibilities: they are enumerable, not an authorization secret. The candidate permits exact lookups to email-verified users; it lacks adequate enumeration/abuse controls, blocking and recovery, and must not be deployed as-is. QR payload parsing does not imply that a scanner or deep link is implemented. Account verification and data access must be enforced in backend rules, not only in the UI. All new IDs and QR payloads are public contact handles, not credentials.

## Required work before test or release

Firebase email/password login verifies an email identity, not ownership of a phone number. Do not fake or imply phone verification. A public mapping from phone numbers to Gmail addresses would expose personal information; do not implement number/password login by returning that mapping to clients or making predictable fake email identities. Firebase Auth provides an email **verification link**, not an email numeric OTP in the basic flow. A reviewed, server-side phone-to-account authentication component with protected mappings, generic errors, independent rate limiting, App Check, account recovery, duplicate handling and deletion is still needed to support real phone-plus-password login without exposing Gmail. Firebase Functions deployment needs the Blaze plan; the owner requested free only. Any alternative must be explicitly evaluated for availability, free quota, privacy and cost before activation. Never store plaintext passwords or service credentials in the app, Git repository or logs. An unverified phone number can be claimed by someone else, so do not treat it as proof of ownership.

Profile photos require a storage design, validated image types and size limits, permissions and retention. Firebase Storage and service/free-tier availability must be checked; do not upload personal photos to an unreviewed public bucket. Before phone or code discovery, decide visibility/consent, protect against enumeration and harassment, preserve contact-request acceptance and blocking, and implement deletion and lifecycle including code reuse. The current test Firestore rules allow only two test UIDs; new email/password accounts cannot use chat under them. Do not change them or enable a new provider in production without a separate migration, testing and explicit approval. Real devices, verified emails, QR camera permission, sign-in, profile access and photo privacy are all untested.

`src/phone-number.js` is an unused syntax-only international number normalizer requiring an explicit country code. It does not check assignment or ownership and does not implement lookup or authentication.

## Local verification test

`integration/email-verification-emulator.js` runs a synthetic email/password signup against local Auth and Firestore emulators only, obtains the email-link code from the emulator's local API (no mail is actually sent), confirms the unverified identity cannot reserve a code, applies the one-time verification code, refreshes the token, reserves an ID, signs out and signs back in. It uses no real project or personal data. Run with `npx firenook emulators:exec --config firebase.browser-emulator.json --project demo-chatbox --only auth,firestore --plain --no-diagnostics 'node --test --test-concurrency=1 integration/email-verification-emulator.js'`. This Firenook test passed locally; it is an alternate simulation, not proof of official emulator or production behavior. The official Firebase Auth and Firestore emulators also passed this synthetic test in CI. Local official emulator execution failed because Java is not installed. This test does not add the account flow to the app, establish real Gmail delivery, validate phone ownership or implement phone-number login.

## Free-tier backend investigation (not implemented or provisioned)

Cloudflare Workers + private D1 is a possible future backend, **not an approved or finished solution**. As of the documentation checked for this work, the Workers Free plan lists 100,000 requests/day; D1 lists 5 million rows read and 100,000 rows written/day, with limits and terms subject to change: https://developers.cloudflare.com/workers/platform/pricing/ and https://developers.cloudflare.com/d1/platform/pricing/. Quota exhaustion can make service unavailable; do not silently upgrade or activate billing. This does not establish that all other app services are free or production-ready.

A separate backend would require an account and deployment, private mapping storage, TLS, careful handling of passwords and Firebase tokens, strict per-account and per-source abuse controls, verified-email enforcement, recovery and deletion, and an independently reviewed protocol. Do not put phone-to-email lookups or signing credentials in the client. Firebase supports server-issued custom tokens (https://firebase.google.com/docs/auth/admin/create-custom-tokens), but any implementation must safeguard signing authority and validate account status and email verification; the availability of the API is not proof the design is secure. No Cloudflare account, database, secret, signing key or service has been created or deployed by this work. Email verification alone cannot prove ownership of a phone number.
